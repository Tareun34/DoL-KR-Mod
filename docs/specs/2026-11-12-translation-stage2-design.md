# 영문 0.5.13.8 추종 2단계(번역) 설계

작성일: 2026-11-12. 선행 문서: `2026-11-10-upstream-0.5.13.8-design.md`(1단계, 병합). 대상 저장소 `Tareun34/DoL-KR-Mod`, `main`.

## 1. 의도와 배경

1단계로 소스는 영문 0.5.13.8 구조가 되었고, 영문이 손대지 않은 자리의 번역은 살아 있다. 영문이 문장을 고친 자리와 새로 추가한 콘텐츠는 영어로 남아 게임이 한영 혼재 상태다. 2단계는 이것을 한글로 되돌리는 작업이다.

사용자 결정(2026-11-12):

- 우선순위는 **기존에 한글로 나왔던 것**, 즉 옛 번역이 밀려난 자리다. 새 콘텐츠는 그 뒤.
- 번역문은 **검수 없이 소스에 바로 넣고 빌드까지** 한다. 사용자는 플레이하면서 이상한 곳을 알려 준다.

### 기록의 성격

`translation/pending/<경로>.json`의 충돌 기록은 "옛 한글(old_kr) ↔ 새 영문(new_en)"이 **줄 단위로 대응하지 않는다**. 영문이 문장 하나를 고친 자리는 거의 1:1이지만, 대사 시스템처럼 구조를 바꾼 파일에서는 옛 한글 11줄이 `<</addSpeechLine>>` 한 줄과 짝지어지는 식이다. 그래서 작업 단위는 기록이 아니라 **파일**이다. 기록은 (1) 그 파일에 번역할 영문이 어디쯤 있는지, (2) 같은 문장의 옛 번역이 무엇이었는지를 알려 주는 참고 자료이고, (3) `translation_status.py`의 완료 판정에 쓰인다.

## 2. 목표 / 비목표 / 금지

**목표**

- 1차 대상 308개 파일에서 영어 산문이 사라지고 한글이 된다. 이어서 2차 118개 파일, 3차 27개 파일.
- 번역이 들어갈 때마다 코드 구조는 그대로다: 매크로, 변수, 링크 대상, HTML 태그, JS 코드가 번역 전과 동일하고, 네 변형 빌드가 성공하며 패시지 이름 집합이 영문과 같다.
- 번역 품질이 기존 번역판과 이어진다: 같은 말투("당신" 서술, NPC별 어조), 같은 이름 표기, 같은 조사 처리.
- 진행 상황이 저장소에 남는다(`translation/STATUS.md`, 묶음별 커밋). 세션이 끊겨도 어디까지 했는지 바로 알 수 있다.
- 빌드할 때마다 서버에 반영되어 사용자가 바로 플레이할 수 있다.

**비목표**

- 영문이 손대지 않아 살아 있는 기존 번역을 고치는 것. 발견되는 오역은 사용자가 말할 때만 고친다.
- 코드만 바뀐 기록 3,160건.
- 이미지 안의 글자, `kr_dict.js` 화면번역 사전의 전면 보강. 새 의상 이름은 소스의 `name:`을 번역하지 않는다(`$worn.lower.name is "naked"` 같은 비교에 1,100여 곳에서 키로 쓰인다). 기존 관례대로 2차·3차에서 `kr_dict.js` 사전에 항목을 추가하는 방식으로만 한글화한다.
- 완료 판정 휴리스틱(`is_done`)의 재설계. 지금의 근사치로 충분하다. 파일 단위로 작업하므로 "그 파일에 영어 산문이 남았는가"를 직접 검사하는 보조 지표를 둔다(4절).

**금지(이렇게 되면 실패)**

- 번역 커밋이 코드 동작을 바꾸는 것. 매크로 이름·인자 구조, `$변수`·`_변수`, `[[링크|대상]]`의 대상, `<<set "m">>`처럼 값으로 쓰이는 문자열이 바뀌면 안 된다.
- 빌드가 깨진 상태로 `dist/`가 갱신되는 것(`build.sh`가 원자적이라 자동으로 막힌다. 빌드 실패를 무시하고 넘어가지 않는다).
- 조사 마커를 모르는 형태로 쓰는 것. 허용 마커: 【은는】【이가】【을를】【와과】【으로로】【아야】【이나나】【이】【이었였】.
- 기존 번역의 이름 표기와 다른 표기가 섞이는 것(예: 에이버리/에버리).

## 3. 방식

### 3.1 작업 단위와 실행자

작업 단위는 **파일 묶음**이다. 한 묶음은 영문 산문 약 300~500줄(기록의 `new_en` 합계 기준)이 되도록 파일을 모으고, 큰 파일(`speech-avery`, `ejaculation` 등)은 한 파일이 한 묶음이거나 패시지 경계로 둘로 나눈다. 묶음 수는 1차 약 50개, 2차·3차 약 20개로 본다.

묶음마다 **번역 에이전트**(서브에이전트, 가장 강한 모델)를 하나 띄운다. 조율자(이 세션)는 묶음을 만들고, 에이전트를 띄우고, 결과를 검사·빌드·커밋한다. 조율자가 직접 번역하지 않는다. 한 번에 동시에 띄우는 에이전트는 3개까지(같은 작업 트리에서 서로 다른 파일만 편집하므로 충돌하지 않는다). 에이전트는 커밋하지 않는다.

### 3.2 번역 에이전트가 받는 것

- 지침서 `translation/TRANSLATOR.md`(이 설계가 정하는 규칙을 에이전트용으로 적은 문서. 저장소에 커밋). 내용: 작업 범위(지정된 파일에서 영어 산문만), 보존해야 하는 것(2절 금지 조항), 말투와 표기 규칙, 조사 마커 목록과 사용법(앞 글자의 받침에 따라 자동 해소되므로 조사 자리에 마커를 쓴다), 변수·매크로 안의 문자열 중 번역하는 것과 안 하는 것의 구분법(옛 번역 기록을 따른다; `<<link "다음">>`·`<<print "...">>`·대사·서술은 번역, `<<set $x to "m">>`·`either("m","f")`·CSS 클래스·패시지 이름은 보존), JS 파일은 사용자에게 보이는 문자열만, 작업이 끝나면 돌려야 하는 명령(`check_translation.py`)과 그 출력이 통과여야 한다는 것, 번역할 수 없거나 애매한 자리는 영어를 남기고 보고하라는 것.
- 담당 파일 목록과 각 파일의 `translation/pending/<경로>.json` 경로.
- 참고 위치: 같은 파일의 옛 번역(기록의 `old_kr`), 이름·용어는 `game/kr_js/kr_dict.js`와 `game/base-system/named-npcs.twee`, 말투는 그 파일에 살아 있는 한글 줄.

### 3.3 검사기 `tools/check_translation.py`

번역 전후의 **구조 스켈레톤**이 같아야 통과한다. 비교 대상은 git `HEAD`의 파일(번역 전)과 작업 트리의 파일(번역 후).

- twee: 파일을 토큰으로 바꾼다. `<<...>>` 매크로는 그 안의 따옴표 문자열 내용을 비워 남기고(`<<link "">>`), 역따옴표 템플릿은 그 안의 매크로·변수만 남기고 글자를 비운다. `[[라벨|대상]]`·`[[대상]]`은 대상만 남긴다(`[[라벨->대상]]` 형식 포함). HTML 태그는 태그 이름과 속성 이름만 남긴다(`<span class="">`). `$변수`·`_변수`·`V.`·`C.npc.`로 시작하는 식별자는 그대로. 그 밖의 글자(산문)는 전부 버린다. 결과 토큰 열이 같아야 한다.
- **텍스트 매크로는 산문으로 본다**(작성자 결정, 빌더 체크 반영). `<<he>>`, `<<He>>`, `<<person1>>`, `<<girl>>`처럼 대명사·명사를 찍는 인자 없는 위젯은 한국어 문장에서 생략·재배치·대소문자 변경이 정상이다(옛 번역 기록 2,400건 중 27%가 이런 차이를 보인다). 이 매크로는 토큰 열에서 빼고 비교한다. 어떤 이름이 텍스트 매크로인지는 **기록에서 산출한다**: `translation/pending`의 충돌 기록에서 옛 영문과 옛 한글 사이에 등장 횟수가 다른 인자 없는 매크로 이름을 모아(대소문자 무시) `translation/text-macros.txt`로 커밋한다. 생성 결과를 눈으로 훑어 `<<else>>`·`<<endevent>>`·`<<exitAll>>`처럼 동작을 바꾸는 이름이 섞이면 뺀다. 그 밖의 매크로(제어문, `<<set>>`, `<<link>>`, `<<= …>>`, `<<print>>`, 인자 있는 위젯 호출, 목록에 없는 인자 없는 위젯)는 모두 구조이며 순서까지 같아야 한다.
- JS: 문자열 리터럴(`"…"`, `'…'`, `` `…` ``)의 내용을 비우고 주석을 지운 코드가 바이트 단위로 같아야 한다. 추가로 `node --check`. **예외(작성자 결정)**: 옛 번역이 한글 단위 표시를 위해 넣어 둔 `counter: "…"` 속성(음식 `foodstuff.js` 103건, `kr_dict.js`의 `getFoodstuffCountKr`가 `food.counter || "개"`로 읽음)은 번역이 **추가**할 수 있다. 검사기는 허용 속성 목록(기본 `counter`)에 든 `이름: "",` 꼴의 줄이 번역 후에만 있는 경우를 무시한다. 같은 유형이 다른 파일에 한두 건 더 있으면(`effect.js`, `children-story-functions.js`) 계획 단계에서 확인해 목록에 넣거나, 번역 커밋과 분리한 "한글판 로직 복구" 커밋으로 처리한다.
- CSS: 번역 대상이 아니므로 변경 금지.
- 조사 마커 검사는 **번역으로 바뀐 줄에만** 적용한다(작성자 결정). 소스에는 이미 허용 목록 밖 마커가 약 35곳(【의】【에게】【도】 등, 20개 파일) 있고 이것은 기존 번역의 버그다(`trSelectPost`가 모르는 마커에 빈 문자열을 돌려줘 조사가 사라진다). 비목표(기존 번역 수정)에 따라 이번에는 두고, 목록을 `translation/LOG.md`에 적어 사용자 판단에 맡긴다.
- 출력: 파일별 `ok` 또는 처음 다른 토큰의 위치(줄 번호)와 앞뒤 토큰. 종료 코드 0/1.
- 보조 지표: 파일에 남은 영어 산문 줄 수(`translation_status.has_prose`와 같은 휴리스틱을 줄 단위로 적용). 통과 조건은 아니고 보고용이다. 이름·고유명사·의도적으로 남긴 영어가 있을 수 있다.

스켈레톤이 보존을 보장하지 못하는 것(알려진 한계, 2026-11-16 검토 반영): (1) 매크로 안 따옴표 문자열의 **값**(`"m"`을 `"남"`으로 바꾸면 통과한다), (2) 여러 줄에 걸친 `[[…]]` 링크(같은 줄 안의 링크만 인식한다). 반대로 다음은 구조로 지킨다: `<<link "라벨" "패시지">>`·`<<button>>`의 두 번째 문자열과 `<<goto "패시지">>`의 문자열(인자가 순수 문자열일 때), JS 템플릿 리터럴 안의 `${…}` 식(식 안의 문자열 리터럴만 번역 가능). 값 변경은 지침서와 옛 번역 참고로 막고, 빌드와 플레이에서 잡는다.

### 3.4 묶음 처리 순서(조율자)

1. 묶음을 정한다(3.5의 순서, 3.1의 크기).
2. 에이전트를 띄운다(동시 최대 3개). 에이전트는 파일을 고치고 `check_translation.py`를 통과시킨 뒤 요약(파일별 남은 영어 줄 수, 남긴 자리와 이유)을 돌려준다.
3. 조율자가 `check_translation.py`를 다시 돌린다(에이전트의 보고를 믿지 않는다). 실패하면 그 묶음을 같은 에이전트에게 돌려보내 고치게 한다. 두 번 실패하면 그 파일을 `git checkout`으로 되돌리고 건너뛴 목록에 적는다.
4. 묶음 3~4개가 끝날 때마다(또는 큰 파일 하나가 끝나면): `./build.sh`, `verify_build.py --names-only`(영문 빌드와), `python3 -m unittest discover -s tools/test -t .`, `translation_status.py`로 STATUS 갱신, 커밋 한 개(`i18n: <디렉터리/파일 요약> (<n>건)`). 빌드가 실패하면 tweego 오류의 파일·줄을 보고 고치거나 그 파일만 되돌린다.
5. 1차가 끝나면 사용자에게 보고하고 플레이 피드백을 받는다. 2차·3차는 같은 절차.

### 3.5 순서

1차(충돌) 안에서: `base-system`(설정·사이드바·공통 위젯) → `base-combat`(대사 파일은 크므로 묶음을 잘게) → `overworld-town` → `overworld-plains`, `overworld-forest`, `overworld-underground` → `04-Variables`(음식·업적·색 이름; JS 문자열) → `special-*`, `base-clothing`, `03-JavaScript`. 디렉터리 안에서는 산문 줄 수가 많은 파일부터.

2차(새 영문 371건)는 1차와 같은 디렉터리 순서. 3차(새 파일)는 `loc-bus/thug.twee`(부랑배, 마을에서 자주 만남) → `loc-mines/*`(광산) → `speech/reaction-*`·`named-npcs-speech` → JS(`settings-ui.js`, `beast-settings.js`의 사용자 노출 문자열) → `sky-testing.twee`(디버그, 마지막).

### 3.6 진행 기록

- `translation/STATUS.md`는 커밋마다 갱신한다(자동 생성).
- `translation/LOG.md`(수동): 묶음 번호, 파일, 결과(통과/되돌림/건너뜀), 에이전트가 남긴 "번역 못 한 자리" 메모. 세션이 끊겨도 여기서 이어간다.
- 커밋은 묶음 단위. 한 커밋에 파일 몇 개~십여 개.

## 4. 검증(각 커밋 전)

1. `python3 tools/check_translation.py <파일들>` 전부 `ok`.
2. `./build.sh` 성공. `python3 tools/verify_build.py /home/chan/game/baseline/en-0.5.13.8.html "dist/DoL-KR 0.5.13.8.html" --names-only` OK.
3. `python3 -m unittest discover -s tools/test -t .`(Herm 가드 포함) 통과. JS를 고친 커밋이면 `(cd server && npm test)`는 불필요(서버 코드 무관).
4. `python3 tools/check_kr_symbols.py check ...` OK(에이전트가 한글판 전용 정의를 지우지 않았는지).
5. STATUS 갱신 후 1차 완료 수가 줄지 않았는지(되돌림 때문에 줄 수 있음; 줄었다면 LOG에 이유).

1차·2차·3차가 끝날 때: 사용자가 플레이로 확인. 이것만 수동이다.

## 5. 작업 순서(계획이 따를 뼈대)

1. `tools/check_translation.py`와 테스트(스켈레톤 추출 규칙 하나하나, JS 문자열 비우기, 조사 마커 검사, 변경이 있을 때 실패·없을 때 통과).
2. `translation/TRANSLATOR.md` 작성. 묶음 생성 도구 `tools/translation_batches.py`(STATUS와 pending에서 3.5 순서·3.1 크기로 묶음 목록을 만들어 `translation/LOG.md`의 표로 출력)와 테스트.
3. 시험 묶음 1개(base-system의 작은 파일 몇 개)로 에이전트 → 검사 → 빌드 → 커밋을 끝까지 돌려 절차를 확인한다. 지침서를 다듬는다.
4. 1차 나머지 묶음을 3.4대로 반복. 끝나면 사용자 확인.
5. 2차, 3차 반복. 각각 끝나면 사용자 확인.
6. 마무리: STATUS·LOG 정리, README의 "0.5.13.8 추종 상태" 절 갱신, `main` 커밋·push.

작업 브랜치는 두지 않고 `main`에서 묶음 단위로 커밋한다(작성자 결정). 이유: 번역 커밋은 독립적이고 되돌리기 쉬우며, `dist/`를 서버가 바로 쓰므로 브랜치와 작업 트리를 분리해도 얻는 것이 없다. 단 각 커밋 전 4절 검증은 지킨다.

## 6. 작업자(계획 작성자·조율자)에게 맡기는 것

- 스켈레톤 토큰화의 세부 정규식과 테스트 픽스처.
- 묶음의 정확한 경계와 큰 파일을 나누는 패시지 경계.
- 에이전트 프롬프트의 문장. 단 3.2의 항목은 모두 들어가야 한다.
- 에이전트 동시 실행 수(최대 3)와 빌드 주기(묶음 3~4개마다)를 상황에 따라 줄이는 것.
- LOG.md의 표 모양.

## 7. 알려진 위험

- 번역 품질은 검수 없이 들어간다. 사용자가 플레이로 발견한 것은 그때그때 고친다(파일과 문장을 알려 주면 된다).
- 스켈레톤 검사는 매크로 문자열의 값 변경을 못 잡는다(3.3). 지침서와 빌드·플레이로 보완.
- 에이전트가 영어를 일부 남기고 "번역 못 함"으로 보고할 수 있다. LOG에 모아 두고 1차가 끝난 뒤 한꺼번에 처리한다.
- 비용: 에이전트 70~100회. 사용자가 수용한 전제(2026-11-12).
- 완료 판정(`is_done`)이 근사치라 STATUS의 완료 수가 실제보다 적게 보일 수 있다. 파일별 "남은 영어 산문 줄 수"를 LOG에 함께 적어 보완한다.
